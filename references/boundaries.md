# Host contracts and boundary examples

Read this when designing host integration or moving code across packages. The requirements in `SKILL.md` are durable; the linked implementations and migration examples below are **2026-11-05 source snapshots**, not current release or installation guarantees.

## Existing contracts to study

The [Desktop application contract](https://github.com/LispMachineLab/lispm-desktop/blob/69d09822a05fa379006359f747f879f7cac586a7/README.org#L475-L516) assigns entrypoints, public status queries, and command declarations to the app. Desktop skins and adapters consume those interfaces from the outside.

[Agent's host callbacks](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/lisp/lispm-agents.el#L91-L130) illustrate useful defaults: `lispm-agents-show-function` uses `pop-to-buffer`, `lispm-agents-main-window-function` uses `selected-window`, `lispm-agents-work-display-function` in [lispm-agents-work.el](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/lisp/lispm-agents-work.el#L29-L32) uses `pop-to-buffer-same-window`, and terminal callbacks use Eat/process operations. [Desktop supplies its implementations](https://github.com/LispMachineLab/lispm-desktop/blob/69d09822a05fa379006359f747f879f7cac586a7/lisp/lispm-desktop-ai.el#L176-L191). The app does not probe for Desktop.

[Stickies' presentation callbacks](https://github.com/LispMachineLab/lispm-stickies/blob/15f6496f0ab322d0152f4da4acdef2870c8271e4/lispm-stickies.el#L275-L349) cover showing, hiding, visibility, the front note, placement, and change events. Ordinary Emacs windows provide the defaults; app data and operations stay in Stickies. Use these as contract examples, not a requirement to copy every hook into every app.

When adding a callback, specify its arguments/result, which buffer or session it concerns, when it runs, and who owns resources. An adapter should install once, remove its own subscriptions on disable, and restore previous callback values only while its own values remain installed. Include failed initialization and repeated enable/disable in lifecycle checks when relevant.

## Agent project views and Office

Reuse [Agent project/group semantics](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/lisp/lispm-agents.el#L1810), [standalone project work filtering](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/lisp/lispm-agents-work.el#L95-L133), and the public [roster API](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/lisp/lispm-agents-roster.el#L268-L284). `lispm-agents-group-by-directory` groups by project despite its name, and `lispm-agents-work-filter` distinguishes `project` grouping from exact `directory` filtering. A directory filter and a project group containing subdirectories/worktrees answer different questions. Preserve identity keys and relationship/status semantics; do not reconstruct them from rendered labels or eagerly read transcripts for list views.

For project-view changes, assign responsibilities explicitly:

- Agent owns scope queries, renderer selection/extension contracts (`lispm-agents-open-project-functions`), host window display callbacks (`lispm-agents-work-display-function`), subscriptions to domain changes, and a usable default project/list view (`lispm-agents-work-mode`).
- Office implements an optional renderer using Agent's public contract.
- Desktop translates sidebar actions into Agent commands (`lispm-agents-open-project`) and owns folding, hit regions, and window/workspace placement.

The design in [Desktop #167](https://github.com/LispMachineLab/lispm-desktop/pull/167) and the earlier Office snapshot (`be4b864a9ce5b330f43fb47b951f7fd5213b8582`) are **boundary counterexamples**: scope/filtering, fallback roster logic, renderer dispatch, subscriptions, and the default list were placed in Desktop, while Office registered a Desktop project-view hook, called `lispm-desktop-platinum-tabs`, and set `lispm-desktop-conversation-buffer`. Those were resolved by moving the project-view contract to Agent ([Agent #146](https://github.com/LispMachineLab/lispm-agent/pull/146)), shared tab controls to UI ([UI #28](https://github.com/LispMachineLab/lispm-ui/pull/28)), renderer integration to Agent/UI APIs ([Office #2](https://github.com/LispMachineLab/lispm-office/pull/2), [Office #3](https://github.com/LispMachineLab/lispm-office/pull/3)), and host adaptation to Desktop ([Desktop #172](https://github.com/LispMachineLab/lispm-desktop/pull/172)). In current source, Office registers on [Agent's project-view hook](https://github.com/LispMachineLab/lispm-office/blob/a7b02eb4b5bd3b4b9d442e44ce8800a43f7371bb/lispm-office-plugin.el#L118) and draws switcher tabs through [`lispm-ui-tabs`](https://github.com/LispMachineLab/lispm-office/blob/a7b02eb4b5bd3b4b9d442e44ce8800a43f7371bb/lispm-office.el#L124-L126).

## Reuse still requires a public API

[ComfyUI's form internals access](https://github.com/LispMachineLab/lispm-comfyui/blob/1e3c762678310f5e2b975d7275caff44034b43ae/lispm-comfyui-simple.el#L393) illustrates cross-package coupling through `lispm-ui-form--*`. A needed public form-update operation belongs in UI; callers should migrate to it. This is source evidence of coupling, not a demonstrated runtime failure.

The shared-UI consumer migrations [Desktop #169](https://github.com/LispMachineLab/lispm-desktop/pull/169), [Desktop #170](https://github.com/LispMachineLab/lispm-desktop/pull/170), [Office #1](https://github.com/LispMachineLab/lispm-office/pull/1), [Desktop #171](https://github.com/LispMachineLab/lispm-desktop/pull/171), [UI #28](https://github.com/LispMachineLab/lispm-ui/pull/28), and [UI #29](https://github.com/LispMachineLab/lispm-ui/pull/29) have merged, moving icons, raster drawing, popups/alerts/menus, lists, scroll bars, title drawing, file dialogs, tabs, and child-frame minibuffer fields to `lispm-ui` while keeping compatibility aliases only in [lispm-desktop-ui-compat.el](https://github.com/LispMachineLab/lispm-desktop/blob/69d09822a05fa379006359f747f879f7cac586a7/lisp/lispm-desktop-ui-compat.el). Recheck status before continuing any migration; compatibility aliases in Desktop do not establish the right ownership for new code.

## Evidence and validation limits

[Agent's no-Desktop source guard](https://github.com/LispMachineLab/lispm-agent/blob/4fcd4972064c72ee80f93e8e1ac432fced5018cd/test/lispm-test.el#L9415-L9422), [Office's production dependency guard](https://github.com/LispMachineLab/lispm-office/blob/a7b02eb4b5bd3b4b9d442e44ce8800a43f7371bb/test/lispm-office-project-test.el#L561-L569), and [Store's production dependency guard](https://github.com/LispMachineLab/lispm-store/blob/af4901b33edefd127dcde514ab6c63699590c18b/test/lispm-store-test.el#L274-L292) support the stronger boundary than “does not require Desktop at load time.” Guards supplement clean-Emacs functional tests; they cannot prove ordinary-Emacs usability, optional-plugin behavior, teardown, or appearance.

Test-only comparisons may legitimately load Desktop, while compatibility aliases may remain in the old Desktop adapter. Inspect the role of the code instead of classifying every textual match as a production dependency. The source survey behind these examples inspected 25 active code repositories; it did not run their apps or certify their runtime independence.
